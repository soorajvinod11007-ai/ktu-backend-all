## 3. Real data facts (design around these)

**Register numbers:** `NIE22CS045` = college `NIE` + 2-digit admission year `22` + 2-letter program code `CS` + 3-digit roll `045`. Batch derived: admission year 22 means batch `2022-26`. Program codes in data: `CS, ME, MC, CE, AD, CC`. One odd prefix exists (`SGI22CS013`): do not reject it, flag it (`is_flagged`).

**Divisions:** Computer Science has two divisions (A and B) in the same batch. Keep them separate in every report. Other programs have no division.

**Grades (KTU 2019 scheme):** `S, A+, A, B+, B, C+, C, D, P, F`, plus `FE` (failed due to attendance/eligibility), `AB` or `Absent`, `Withheld`, `TBP` (to be published). `No change` appears only in revaluation PDFs and means nothing changes; never store it as a grade. Grades F, FE, Absent are not passes. `TBP` and `Withheld` are their own statuses.

**Result statuses:** `pass, fail, absent, withheld, tbp`.

**Backlog students:** students from older batches appear in newer exams (example: `NIE21ME003` in an S1 2022 exam). A result row links to the student and to the exam session, never assumes the student's own batch matches the exam's batch.

**Supply paper** = a course a student failed or was absent for and has not yet cleared in a later exam.

## 4. The input files (what the parsers must read)

All come from KTU or the college. Sample files are in `/samples` (ask me if missing). Four PDF types plus one Excel:

1. **Student list Excel** (`CS_ME_MC_CE.xlsx`): register numbers and names. This is the master list: "registered" counts and pass % depend on it, because result PDFs only list problem students.
2. **Result PDF** ("Exam Centre ... B.Tech S1 (S,FE) S2 (S,FE) Exam Dec 2024 ... Generated on ..."): per program, a course-code/course-name table, then a table `Register No | Course Code (Grade)` such as `NIE23CS011  MAT101(F), CYT100(F), EST100(Absent)`. **It lists only students with a fail, absent, withheld, TBP, or (in revaluation PDFs) changed result.** Students not listed passed everything they registered for. Lines wrap across rows, program headings vary in spelling ("COMPUTER SCIENCE & ENGINEERING" and "COMPUTER SCIENCE AND ENGINEERING" are the same program; "Computer Science and Engineering (Cyber Security)" is CC). Header gives the exam name and generated date. Page footer gives the date and "Controller of Examinations".
3. **Revaluation result PDF**: same layout, title begins "Revaluation Result-". Entries like `MAT101(No change)`, `MAT101(P)`, `EST110(D)`: a new grade replaces the old one and must be written to result history.
4. **Semester Grade Card PDF** ("Semester Grade Card Report"): header has Institution, Branch, Semester. A legend maps course codes to titles. Then a table `Student | course columns... | Earned Credits | Cumulative Credits | SGPA | CGPA`, where `Student` is `REGNO-NAME` (names wrap across lines, e.g. `NIE22CS052-UMMUFASEELA K A`). Column headers wrap (`MAT10` / `1`). An empty grade cell means the student did not take that course. Grades here are the full per-course grades, so this is the richest source and gives SGPA and CGPA.
5. **Course Book PDF** ("Course Book Details For ..."): Program, Branch, Semester, Academic Year, then per slot (A, B, C, D, E, S, T): Course Code, Course Name, and a faculty table: `Name of Faculty (KTU-F25319) | Contact | Email | Batch (2022-2023) | Main Faculty Yes/No | QP Setter`. Phone and email wrap across lines. A course can have two faculty rows (e.g. EST120 Part I Civil and Part II Mechanical; the second has Main Faculty = No). Some pages are truncated (a slot with no faculty table): record the course with no faculty and warn.

PDFs have wrapped table cells and text-extraction artifacts (words glued together, e.g. `...CALCULUSEST102`). Prefer `pdfplumber` table extraction, fall back to line-based regex, and **always validate parsed output**: every register number must match the pattern, every grade must be in the allowed set, every course code must be known or flagged. Never silently drop a row; report it as a parse error with page and row.

## 5. The reports the principal needs (Phase 7 output)

From the circular, formats 5 to 9 are generated by this system. Formats 1 to 4 come from KTU and the Jyothi app and are NOT built.

1. **Course-wise Faculty-wise Performance** (per program, batch, division, semester, academic year). Rows per course: course code, title, faculty, registered, appeared, absent, pass, fail, withheld, pass % w.r.t. registered, pass % w.r.t. appeared, remarks. Plus: supply-paper status table (number of students with 0, 1, 2 ... 8 supply papers and a total), overall performance (registered for the semester exam, appeared for all exams, cleared all courses, class ALL-PASS %), and top 3 class toppers by SGPA.
2. **Faculty Performance History**: one faculty member's courses across batches and academic years, same columns.
3. **Student-wise Supplementary Status**: per student, supply papers in each of S1..S8, total, total courses, CGPA; plus a summary of how many students have 0..8 supply papers.
4. **Program and Semester-wise** (by academic year): per program, batch, semester: registered (regular), successfully passed, pass %, and an overall total and average. **A filled sample for AY 2025-26 exists. Your computed numbers must match it** (see section 9).
5. **Graduation Statistics**: per batch and program: registered for S8, graduated with zero supply, graduation %.

Each report has JSON, PDF and Excel versions in the NiCE printed layout (title "NIRMALA COLLEGE OF ENGINEERING TECHNOLOGY AND MANAGEMENT", report name, Program/Batch/AY/Semester header, signature lines KTU Coordinator and Principal).

### Phase 5: Upload and PDF parsing pipeline
Endpoints: `POST /uploads/preview` (multipart `file`, `file_type` = student_list | course_book | grade_card | result | revaluation, optional `exam_session_id`), `POST /uploads/{id}/confirm`, `DELETE /uploads/{id}`, `GET /uploads`.

- One parser class per file type behind a common interface: `parse(file) -> ParseResult(rows, errors, meta)`. Put them in `app/modules/uploads/parsers/`. Parsing is pure (no database); a separate service matches parsed rows to the database.
- **Two steps always.** Preview parses, validates, matches students and subjects, stores the parsed payload (JSON, or a staging table) linked to an `upload_logs` row, and returns summary counts (total, ok, with errors, new, updates), sample rows and all errors (`{page, row, code, message}`). Nothing touches real tables. Confirm saves everything in one transaction, rolls back fully on failure, and refuses a second confirm of the same upload.

- Per type: student list creates or updates students (derive program, batch, flag odd prefixes; create divisions as needed; CS division A or B comes from the sheet or a column if present, otherwise ask via an error the admin resolves); course book creates faculty (match on `ktu_id`), subjects if missing, and `course_offerings`; grade card creates `semester_results` for every course column with a grade (blank = not taken) and a `grade_cards` row with credits, SGPA, CGPA; result PDF creates results with status fail/absent/withheld/tbp for listed students (see Phase 6 for how passes are inferred); revaluation updates the grade, writes `result_history` with old and new values, and does nothing for "No change".

- Tests use the sample files and must cover: every parser on real samples, wrapped names and wrapped cells, glued text, odd prefix, unknown register number, preview-saves-nothing, confirm atomicity, double confirm, duplicate file, wrong declared type, malicious file name and oversized file.

### Phase 6: Business logic
Pure, well-tested functions in `app/modules/results/` (a `rules.py` plus service methods):

- **Classification:** pass / fail / absent / withheld / tbp from grade. Absent and withheld are not "appeared" for the appeared count (define precisely and document: appeared = registered minus absent minus withheld minus tbp).
- **Registered** for a course in an exam = students (from the master list, correct program, batch, division) enrolled for that course in that semester, plus backlog students who sat that exam. Because result PDFs list only problem students, **passes are inferred**: a registered student with no fail/absent/withheld entry for that course passed. Where a grade card exists, prefer its explicit grades over inference and report any disagreement.
- **Supply tracking:** a course is a supply paper while the latest attempt is F, FE, or Absent. A later passing attempt clears it. Provide `get_supply_papers(student, as_of)` and counts per semester S1..S8.
- **Pass percentages:** w.r.t. registered and w.r.t. appeared, rounded to 2 decimals, safe against division by zero.
- **Program-semester pass %:** a student "successfully passed" a semester when they have no failed, absent or withheld course in that regular attempt. This is the definition used by the filled AY 2025-26 sheet; verify against it and tell me if the sheet implies a different rule.
- **Class all-pass %**, **cleared all courses**, **toppers** (top 3 by SGPA, ties shown together), **graduation** (registered for S8 and zero supply papers after S8).
- Revaluation and supply exam changes must update results and keep history; recomputation always reads the latest state.
- Property-style tests on the rules plus table-driven tests with hand-computed numbers from the sample PDFs.
